Chapter 05

The authentication flow

Knowing what a token is gets you halfway. The other half is the choreography: how a token is issued at login, attached to each request, and quietly renewed before it expires — without ever sending the user back to the login screen. This chapter walks the whole dance.

Two tokens, two jobs

Most production JWT setups don't use one token — they use two, with deliberately different lifetimes. Understanding why is the key to everything that follows.

An access token is the workhorse: it's short-lived and travels on every request to prove you're allowed in. A refresh token is the quiet backup: it's long-lived, kept somewhere safe, and used for one thing only — getting a fresh access token when the current one runs out.

Access tokenRefresh token
LifetimeShort — 5 to 15 minutesLong — days to weeks
Sent…On every API requestOnly to the refresh endpoint
PurposeGrants access to resourcesObtains new access tokens
If stolenLimited window of abuseHigh impact — guard it closely
StoredMemory / short-lived storeHttpOnly cookie / secure store

The pay-off: because the access token expires fast, a stolen one is useful only briefly. But because the refresh token can mint replacements, the user isn't forced to log in every few minutes. Short blast radius and a smooth experience.

Step 1 — Logging in

The user submits credentials once. The auth server checks them and, if they're good, signs and returns both tokens — typically as JSON:

{
  "access_token":  "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refresh_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type":    "Bearer",
  "expires_in":    900
}

expires_in here is 900 seconds — fifteen minutes — for the access token. The client stashes both tokens and is ready to make authenticated calls.

Step 2 — Using the access token

On each request to a protected resource, the client attaches the access token in the Authorization header using the Bearer scheme:

GET /api/orders HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...

“Bearer” means exactly what it sounds like: whoever bears (holds) the token gets access — there's no extra proof of identity. That's why transport security and short lifetimes matter so much. The API verifies the signature and the claims (Is it expired? Is the audience me?) locally, with no session lookup, and serves the request. If the token is missing or invalid it returns 401 Unauthorized; if the token is valid but lacks permission, 403 Forbidden.

Step 3 — Refreshing

Eventually the access token expires and the API answers a request with 401. Rather than bouncing the user to a login form, the client sends its refresh token to a dedicated endpoint and gets a new access token back:

POST /auth/refresh HTTP/1.1
Host: auth.example.com
Content-Type: application/json

{ "refresh_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9..." }

The auth server validates the refresh token, and — if all is well — issues a fresh access token. The client then quietly retries the original request. From the user's perspective, nothing happened.

Refresh-token rotation

A refresh token is powerful and long-lived, which makes it a juicy target. Rotation shrinks that risk: every time a refresh token is used, the server issues a new refresh token alongside the new access token and invalidates the old one. A given refresh token works exactly once.

This also gives you theft detection almost for free. If an attacker steals a refresh token and uses it, the legitimate client's copy is now stale. When the real client next tries to refresh with that now-invalid token, the server sees a reused token — a strong signal of compromise — and can revoke the entire token family, forcing a fresh login.

Rotation in one lineOne-time-use refresh tokens turn a silent theft into a noisy, detectable event — and limit how long a stolen one stays useful.

Lifetimes & expiration

The whole model leans on the time claims doing their job. exp (expiration) and nbf (not-before) are checked on every verification, usually with a small allowance for clock skew (a minute or two) so that slightly out-of-sync servers don't reject valid tokens.

There's no universal "correct" lifetime, but sensible defaults look like this:

TokenTypical lifetimeWhy
Access token5–15 minutesShort enough that a stolen one expires quickly
Refresh tokenHours to weeksLong enough to avoid constant logins; rotated on use
Clock-skew leeway≤ 1–2 minutesTolerates minor server time drift, no more

Don't stretch the access tokenMaking access tokens long-lived to "avoid the hassle of refresh" throws away the whole security benefit. Keep them short and let the refresh flow do its job.

Logging out & revocation

Here's where stateless bites back. Because a signed access token is self-contained, the server can't "cancel" it before it expires — there's nothing to delete. A practical logout therefore combines a few moves:

  • Discard the tokens client-side — clear the cookie or memory so the browser stops sending them.
  • Revoke the refresh token server-side — rotation already invalidates old ones; an explicit denylist (keyed by the jti claim) handles immediate revocation.
  • Keep access tokens short — so the brief window where a discarded-but-unexpired access token still works is small.

For systems that truly need instant, global revocation of access tokens, you're partly stepping back toward stateful checks (a denylist or a quick "is this still valid?" lookup) — a reminder that JWTs trade revocation control for statelessness.
