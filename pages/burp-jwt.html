Working with JWTs in Burp Suite

Burp Suite, with the free JWT Editor extension, is the tool you'll reach for on essentially every JWT lab and authorized test. It decodes tokens, lets you edit and re-sign them, manages keys, and packages the trickier attacks behind a button. This is the hands-on workflow.

Authorized targets onlyUse this against PortSwigger's Web Security Academy labs or systems you're explicitly permitted to test.

Install the JWT Editor extension

In Burp, open Extensions → BApp Store, find JWT Editor, and install it (it works in Community and Professional). It adds two things: a JSON Web Token tab in the message editor (visible in Proxy and Repeater whenever a request contains a JWT), and a JWT Editor Keys tab in Burp's main window for managing the keys you'll sign with.

Reading & editing a token

Capture a request carrying a token (the Authorization: Bearer header or a cookie), then send it to Repeater. Switch to the JSON Web Token tab and you'll see the header and payload decoded into editable text. Change whatever you're targeting — typically a privilege claim such as role or an identity claim like sub — and Burp re-encodes the parts for you. Sending it as-is (without re-signing) is exactly how you test whether the server bothers to verify the signature at all.

Managing keys

Attacks that need a valid-looking signature require a key. On the JWT Editor Keys tab you can:

  • Generate an RSA key — a fresh key pair for jwk/jku injection, where the server will trust the key you supply.
  • Import a key from JWK or PEM — e.g. a public key you pulled from the target's /.well-known/jwks.json.
  • Create a symmetric key — needed for the algorithm-confusion attack, where the target's public key (as PEM) becomes your HMAC secret.

Signing

After editing the token, use the Sign button on the JSON Web Token tab. You pick which key to sign with and the algorithm, and choose how the header is handled — leave it as is, or have the extension embed your public key via the jwk parameter. This is the manual path; for the common attacks there are one-click helpers.

Built-in attacks

The Attack dropdown on the JSON Web Token tab automates the fiddly bits:

AttackWhat it doesTargets
Embedded JWKGenerates a key, embeds the public half in the jwk header, and signs with itjwk injection
Sign with alg:noneSets alg to a none variant and strips the signatureno-signature
Key confusion (manual)Sign HS256 using a symmetric key created from the target's public-key PEMalgorithm confusion

For the none case, the resulting header is simply:

{ "alg": "none", "typ": "JWT" }

For kid path traversal you won't need a helper — just edit the kid value in the header (e.g. ../../../../../dev/null) and sign with an empty symmetric key.

Scanning

Burp Scanner (Professional) flags some JWT issues automatically, but the real work — tampering claims, swapping algorithms, injecting keys — happens by hand in Repeater with the JSON Web Token tab. Treat the scanner as a first pass, not a substitute.

A lab workflow

1

Capture

Browse the lab through Burp's proxy until you have an authenticated request carrying the token.

2

Send to Repeater

Right-click → Send to Repeater, then open the JSON Web Token tab.

3

Edit the claim

Set the claim that proves impact — often sub to administrator.

4

Pick the attack

Send unsigned to test verification; or use Embedded JWK, alg:none, a cracked secret, or key confusion depending on the flaw.

5

Send & confirm

Replay the request and check you've reached the protected function.
