OpenID Connect

“Sign in with Google” isn't magic — it's OpenID Connect, a thin authentication layer on top of OAuth 2.0. Its defining feature is the ID token, a JWT that tells your app who just logged in. Here's the real flow, end to end, and how to validate what you get back.

OIDC vs. OAuth, in one line

OAuth 2.0 answers “what may this app do?” (authorization). OpenID Connect adds “who is this user?” (authentication) and standardises the answer as an ID token. If you only need API access, OAuth suffices; if you need to log a user in, you want OIDC. (Background: OAuth vs JWT.)

The ID token

The ID token is a JWT issued to your application asserting the user's identity. Alongside the usual iss/sub/aud/exp/iat, it carries identity-specific claims:

{
  "iss": "https://accounts.example.com",
  "sub": "248289761001",            // stable user identifier
  "aud": "your-client-id",          // YOUR app — must match
  "exp": 1735689600,
  "iat": 1735686000,
  "auth_time": 1735685990,          // when the user authenticated
  "nonce": "n-0S6_WzA2Mj",          // must match what you sent
  "email": "ada@example.com",
  "name": "Ada Lovelace"
}

The sub is the durable key you should tie your local account to — not the email, which can change. The aud must equal your client ID, and the nonce must equal the one your app generated, or the token isn't yours to trust.

The Authorization Code flow with PKCE

This is the recommended flow for essentially all app types today. Six steps:

1

Redirect to the provider

Your app sends the user to the authorization endpoint with scope=openid …, a state, a nonce, and a PKCE code_challenge.

2

User authenticates & consents

At the provider (Google, etc.) — your app never sees their password.

3

Provider redirects back with a code

A short-lived authorization code plus your state (which you verify matches).

4

Exchange the code for tokens

Your app calls the token endpoint with the code and the PKCE code_verifier and receives an ID token + access token (+ maybe a refresh token).

5

Validate the ID token

Check signature, iss, aud, exp, and nonce (see below).

6

Establish the session

Map sub to your user, and use the access token for any API calls.

The authorization request (step 1) looks like this:

GET https://accounts.example.com/authorize?
    response_type=code
  &client_id=your-client-id
  &redirect_uri=https://app.example.com/callback
  &scope=openid%20profile%20email
  &state=xyz123
  &nonce=n-0S6_WzA2Mj
  &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  &code_challenge_method=S256

Why PKCE

PKCE (Proof Key for Code Exchange) stops a stolen authorization code from being useful. Your app invents a random code_verifier, sends only its hash (code_challenge) in step 1, and reveals the verifier itself only in step 4. An attacker who intercepts the code can't exchange it without the verifier. It began as a mobile/public-client protection and is now recommended for all clients.

Scopes, claims & userinfo

The openid scope is what makes a request OIDC at all. Adding profile or email asks for those claim sets, which may arrive in the ID token or be fetched from the userinfo endpoint using the access token. Request only the scopes you actually need.

Validating the ID token

An ID token is only trustworthy after these checks — most handled by a good library, but all essential:

import * as jose from 'jose';

const JWKS = jose.createRemoteJWKSet(
  new URL('https://accounts.example.com/.well-known/jwks.json'));

const { payload } = await jose.jwtVerify(idToken, JWKS, {
  issuer:   'https://accounts.example.com',  // iss
  audience: 'your-client-id',                // aud == your client
});                                          // signature + exp/iat enforced

if (payload.nonce !== expectedNonce) {       // nonce you generated
  throw new Error('nonce mismatch');
}

Don't identify users with the access tokenThe access token is for calling APIs; the ID token is what proves identity to your app. Mixing them up is a classic OIDC bug — see access vs ID tokens.

Discovery

Rather than hard-coding endpoints, OIDC providers publish a discovery document at /.well-known/openid-configuration listing the authorization, token, userinfo, and jwks_uri endpoints. Your app reads it once and wires itself up — including where to fetch keys for validation (see JWKS & Key Rotation).

Pitfalls

Watch out forUsing the deprecated implicit flow (use Authorization Code + PKCE) · skipping nonce or aud validation · trusting an ID token without verifying its signature · confusing ID and access tokens · requesting more scopes than you need.
