Service-to-service auth

Tokens aren't only for users. In a microservice world, services call services — sometimes on their own behalf, sometimes carrying a user's identity through a chain of hops. This chapter covers both: machine-to-machine tokens, and how to propagate identity downstream without handing every service the keys to the kingdom.

Machine-to-machine tokens

When there's no human — a cron job, a backend worker, one API calling another — the caller authenticates as itself. The standard mechanism is OAuth 2.0's client-credentials grant: the service presents its client ID and secret (or a signed client assertion) to the authorization server and receives an access token representing the service.

POST /oauth/token HTTP/1.1
Host: auth.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id=orders-service
&client_secret=••••••••
&audience=https://inventory.example.com
&scope=inventory.read

The returned token's sub is the service, its aud is the API being called, and its scope is narrowed to what the job needs. Treat the client secret like any signing key — store it in a vault and rotate it.

Propagating user identity

Now the harder case. A request enters at a gateway, which calls Service A, which calls Service B. How does B know which user this is for? Two approaches:

Pass-through

Forward the user's original token downstream. Simple — but every service can now use that token, its aud doesn't really fit B, and a leak anywhere is a leak everywhere.

Token exchange

Service A swaps the incoming token for a new one scoped and audienced for B. Least privilege, correct audience, and a recorded delegation chain.

Token exchange (RFC 8693)

Token exchange lets a service trade one token for another with a different audience, narrower scope, or an added actor. Service A sends the user's token to the authorization server and gets back a token meant specifically for B — still tied to the user, but minimal.

POST /oauth/token HTTP/1.1
grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=eyJhbGciOiJSUzI1Ni␣...   // the user's token
&subject_token_type=urn:ietf:params:oauth:token-type:jwt
&audience=https://serviceB.example.com
&scope=orders.read

The exchanged token can carry an act (actor) claim recording that Service A is acting on the user's behalf — a useful audit trail when a call crosses several services.

mTLS & service identity

Authenticating which service is calling is often done at the transport layer with mutual TLS: each service holds a certificate, and connections are only accepted from peers presenting a trusted one. This pairs naturally with certificate-bound tokens (see DPoP & mTLS). In practice a service mesh (Istio, Linkerd) frequently provisions and rotates these certificates and enforces mTLS for you, so application code carries only the user-identity token.

Practical patterns

  • Verify at the edge, propagate internally. The gateway validates the user's token once, then mints or exchanges narrow internal tokens for downstream calls.
  • One audience per service. Give each service tokens addressed to it, so a token for A can't be replayed against B.
  • Keep internal tokens short-lived. Minutes, not hours — limit the blast radius inside the mesh.
  • Don't trust the network. “Internal” isn't “safe” — verify tokens (and ideally mTLS) even between your own services.

Pitfalls

Watch out forAudience confusion — one token accepted everywhere (see missing aud check) · over-broad scopes propagated unchanged · long-lived service secrets that never rotate · assuming the internal network is trusted · forwarding a user token to a service that logs it.
