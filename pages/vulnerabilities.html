Chapter 07

The vulnerability catalogue

Almost none of these weaknesses are flaws in JWT the format. They live in how tokens are handled — the verification call, the key management, the claim checks. The good news: knowing each attack hands you its defense. Here are sixteen, grouped and paired with detection and prevention.

Defensive framingThis catalogue is for building and reviewing secure systems. Several issues are demonstrated safely, on fabricated tokens, in the attack demos. Only test these against systems you own or are authorized to assess.

A striking number of these collapse under a single habit: verify properly, with the algorithm pinned — never just decode, and never trust the token's own alg.

import jwt from 'jsonwebtoken';

// ❌ NEVER trust a decoded token — decoding does NOT verify anything
const unsafe = jwt.decode(token);            // attacker-controlled data

// ✅ Verify with the algorithm pinned and the claims checked
const claims = jwt.verify(token, KEY, {
  algorithms: ['RS256'],                     // pin it — defeats alg confusion & none
  issuer:   'https://auth.example.com',      // check who issued it
  audience: 'https://api.example.com',       // check it was meant for you
  clockTolerance: 60                          // small skew only; exp/nbf enforced
});

Algorithm & signature attacks

An attacker sets the header to {"alg":"none"} and removes the signature. Libraries that honour it skip verification and accept a fully forged token.

Detect  Send a token with alg:none (and a tampered payload) and see if it's accepted; review code for verification that branches on the header's algorithm.

Prevent  Pin allowed algorithms server-side and reject none outright. See the demo →

The server expects RS256 and verifies with an RSA public key. The attacker switches the header to HS256 and signs using that public key as the HMAC secret. A verifier that picks the algorithm from the header will accept the forgery — because the “secret” is public.

Detect  Take a known RS256 token, re-sign an HS256 variant with the public key as the secret, and test acceptance. See the Algorithms chapter.

Prevent  Pin a single expected algorithm; never let one key be used under two algorithm types.

The code decode()s a token and trusts its claims without ever calling verify(). The signature is decorative; anyone can forge claims.

Detect  Grep for decode used to read identity/roles; send a token with a garbage signature and a tampered payload and see if it's trusted.

Prevent  Always verify before reading claims, and make verification failure fatal. Tampering demo →

With HS*, the signature is only as strong as the secret. A short or dictionary secret can be recovered offline; then the attacker mints any token.

Detect  Run a wordlist/brute-force against a captured token (offline); audit config for hard-coded or low-entropy secrets.

Prevent  Use a long, random secret (≥256 bits) from a CSPRNG; consider asymmetric keys so verifiers can't sign. Brute-force demo →

Undersized RSA keys (e.g. 1024-bit) weaken the signature's security margin over time.

Detect  Inspect the public key length; flag anything under 2048-bit.

Prevent  Use RSA ≥ 2048-bit (3072+ for longer horizons), or switch to ES256 / EdDSA for strong, compact keys.

Header-injection attacks

The header can carry fields that tell the verifier which key to use. If the server trusts them blindly, the attacker chooses the key.

The kid (key ID) header selects a verification key. If it's used to build a file path or SQL query, an attacker can point it at a file they control, traverse the filesystem, or inject SQL — sometimes coercing the server into verifying with a key they know.

Detect  Try path-traversal and SQL metacharacters in kid; review how kid maps to a key.

Prevent  Treat kid as an opaque lookup against an allow-list of known keys; never feed it into file paths or queries.

The jku header points to a URL hosting the JSON Web Key Set. If the server fetches whatever URL the token names, an attacker hosts their own key and signs forged tokens that “verify”.

Detect  Set jku to an attacker-controlled (or SSRF-reachable) URL and test acceptance.

Prevent  Ignore jku from the token; fetch keys only from a pre-configured, allow-listed endpoint.

The jwk header can embed a full public key inside the token. A naive verifier validates the signature against that embedded key — so the attacker simply ships their own key and a matching signature.

Detect  Embed a self-generated key in the jwk header, sign with its private half, and test.

Prevent  Never verify against keys supplied by the token; only use server-side trusted keys.

Claim & validation flaws

No exp claim, or a verifier that ignores it, yields tokens that live forever — a stolen one never stops working.

Detect  Replay an old/expired token; decode tokens and check for a sensible exp.

Prevent  Always set a short exp and enforce it (and nbf) with minimal clock skew. Expiry demo →

Without checking aud and iss, a token minted for one service (or by a different issuer) may be accepted by another — token “confusion” across systems.

Detect  Present a valid token from a sibling service/audience and see if it's accepted.

Prevent  Validate aud against your service and iss against an allow-list on every verification.

Verification that “logs and continues” on error, catches exceptions too broadly, or checks only some claims effectively trusts invalid tokens.

Detect  Review error handling around verification; fuzz with malformed tokens and confirm they're rejected, not waved through.

Prevent  Treat any verification failure as a hard reject; rely on a vetted library's full checks rather than ad-hoc logic.

A captured token is re-sent by an attacker. While it's valid, it works — JWTs are bearer credentials.

Detect  Capture a token and replay it from another client/context.

Prevent  Short lifetimes, TLS everywhere, and for sensitive flows a one-time jti tracked server-side; consider sender-constraining (DPoP / mTLS).

Data exposure & storage

The payload is only Base64URL-encoded — readable by anyone holding the token. Passwords, secrets, or excess PII placed there are effectively exposed.

Detect  Decode tokens and inspect the payload for anything that shouldn't be public.

Prevent  Carry only non-sensitive claims; keep sensitive data server-side, or encrypt the token (JWE). See Structure.

If the HMAC secret or RSA/EC private key leaks — via source code, logs, repos, or config — an attacker can forge unlimited valid tokens. Game over.

Detect  Scan repos/CI logs/images for secrets; monitor for unexpected token issuance.

Prevent  Store keys in a secrets manager/KMS, never in code; rotate regularly and on suspicion; scope key access tightly.

Tokens in localStorage are reachable by any JavaScript on the page — so a single XSS flaw lets an attacker read and exfiltrate them.

Detect  Check where tokens are stored; review the app's XSS surface and CSP.

Prevent  Prefer HttpOnly, Secure, SameSite cookies so script can't read the token; keep access tokens short; fix XSS at the source and deploy a strong CSP.

Storing a token in a cookie dodges XSS reads but reintroduces CSRF: browsers attach cookies automatically, so a forged cross-site request can ride the user's token.

Detect  Attempt a cross-site state-changing request and see if the cookie is honoured without an anti-CSRF check.

Prevent  Use SameSite=Lax/Strict cookies, anti-CSRF tokens for state-changing requests, and verify Origin/Referer.

The through-linePin the algorithm, verify before you trust, validate exp/aud/iss, never trust token-supplied keys, protect the signing key, and store tokens carefully. Do those and most of this list simply can't happen.
