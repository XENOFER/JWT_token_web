OAuth vs JWT

It's one of the most common questions in web security — and a slightly unfair one, because the two aren't really competitors. One is a format; the other is a framework. Sorting out which is which (and where OpenID Connect and plain sessions fit) makes the whole landscape click into place.

They're not really rivals

Asking “OAuth or JWT?” is a bit like asking “engine or fuel?” They operate at different layers and are frequently used together. In a nutshell:

  • JWT is a token format — a way to package signed claims as a string.
  • OAuth 2.0 is an authorization framework — a set of flows for granting an application limited access to resources.
  • OpenID Connect (OIDC) is an authentication layer on top of OAuth 2.0 — it adds “who is this user?”.
  • Sessions are the stateful baseline — the classic server-side alternative to token-based auth.

A typical real-world login uses several at once: an OAuth 2.0 flow (the framework) returns tokens, those tokens are often JWTs (the format), and if you're logging a user in rather than just authorizing API access, OpenID Connect (the layer) supplies an ID token — which is itself a JWT.

What each one actually is

A compact, signed way to represent claims as header.payload.signature. It says nothing about how you obtain or exchange one — only how it's structured and verified. JWTs show up as access tokens, ID tokens, and more.

A framework that lets a user grant an application limited access to their data on another service — without sharing their password. Think “Let this app read your Google Calendar.” It defines roles (resource owner, client, authorization server, resource server), scopes, and grant flows, and it issues access tokens (and usually refresh tokens). Crucially, OAuth does not require those tokens to be JWTs — they can be opaque random strings instead.

OAuth answers authorization (“what may this app do?”), not authentication (“who is the user?”). Using it as a login mechanism on its own is a classic mistake.

A thin layer built on top of OAuth 2.0 that adds proper authentication. Its key addition is the ID token — always a JWT — which states who the user is (and when/how they authenticated). “Sign in with Google/Apple/Microsoft” is OIDC. If you need to know the user's identity, this is the standard you want, not raw OAuth.

The traditional approach: the server stores session state and hands the browser an opaque session ID in a cookie. Simple, instantly revocable, and ideal for server-rendered first-party apps — but it requires shared session storage to scale. This is the alternative JWT-based stateless auth is usually compared against (see the What is JWT chapter).

How they fit together

The cleanest mental model is layered: OpenID Connect sits on OAuth 2.0, and the tokens flowing through both are commonly formatted as JWTs.

Access token vs. ID token

OIDC hands you two tokens with very different purposes, and mixing them up is a frequent security bug:

Access token → APIs

Proves authorization. Send it to resource servers to call APIs. The API is its intended audience. May be a JWT or opaque.

ID token → your app only

Proves authentication to your client. Don't send it to APIs as a credential, and don't treat an access token as proof of identity.

When to use what

1

First-party app, you own client and server

Your own JWT-based auth — or plain sessions — is perfectly reasonable. No need for the full OAuth machinery.

2

“Log in with Google / GitHub / Apple”

Use OpenID Connect. It's the standard for federated identity, and the ID token tells you who signed in.

3

Third-party apps acting on a user's behalf

Use OAuth 2.0 with scopes, so users grant narrow, revocable access without sharing credentials.

4

You need instant revocation / server-rendered pages

Sessions are often the simplest correct answer. Don't reach for JWTs reflexively.

Common pitfalls

Watch out forUsing OAuth 2.0 as a login system (it's authorization — use OIDC for identity); rolling your own OAuth/OIDC instead of a vetted provider; treating a JWT as a whole session without short lifetimes and refresh; and confusing the ID token with the access token.
