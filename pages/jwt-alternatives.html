JWT alternatives

JWT won the popularity contest, but it isn't the only way to carry a token — and several of its sharpest edges (algorithm agility, none, format complexity) simply don't exist in the alternatives. Knowing them makes you a better engineer, even if you stick with JWT.

Why look beyond JWT?

Most JWT vulnerabilities trace back to its flexibility: the header lets a token declare its own algorithm, which is the root of algorithm confusion and none. The alternatives below take different stances — some remove algorithm choice entirely, some drop client-readable claims, some add powerful delegation. None is a silver bullet, but each is worth knowing.

PASETO

PASETO (Platform-Agnostic Security Tokens) is the most direct “safer JWT.” Instead of a negotiable alg header, it ships versioned protocols: each version pins one modern, vetted cipher suite, so there's no algorithm field to attack and no none. Tokens also declare a purpose — local (symmetric, encrypted) or public (asymmetric, signed):

v4.public.eyJzdWIiOiIxMDI0Ii4uLn0.Q2pK…signature

version · purpose · payload · authentication

The shape resembles a JWT, but the crucial difference is up front: v4.public fully determines the cryptography. There is no “pick your algorithm,” which closes a whole class of attacks by design. PASETO is an excellent default when you control both issuer and verifier and want JWT-like ergonomics with safer guarantees.

Branca

Branca is a compact, opaque token using authenticated encryption (XChaCha20-Poly1305) with a built-in timestamp. The contents are always encrypted, so unlike a JWS there's nothing readable inside, and the format is deliberately tiny and rigid. It's a good fit for stateless, symmetric, encrypted tokens where you don't need a public-key model.

Macaroons

Macaroons bring a trick the others don't: attenuation. A holder can add caveats — extra restrictions like “read-only” or “expires in 5 minutes” — to a macaroon without the signing key, producing a more limited token. That makes them powerful for delegation: hand someone a narrowed token they can narrow further but never broaden. The trade-off is conceptual complexity and a smaller ecosystem.

Opaque tokens + introspection

The oldest alternative is to make the token carry no information at all: a random reference string. The resource server validates it by calling the authorization server's introspection endpoint (RFC 7662), which returns whether it's active and its claims. This is essentially stateful — which means instant revocation is trivial and nothing is client-readable — at the cost of a network call (usually cached) per validation. Classic OAuth deployments use this heavily.

How to choose

Rules of thumbNeed broad ecosystem/library support or OIDC interop → JWT. Control both ends and want JWT-like tokens with safer defaults → PASETO. Need easy, instant revocation → opaque + introspection. Need delegated, attenuable capabilities → macaroons. Want a tiny, always-encrypted symmetric token → Branca.

Pitfalls

Watch out forSwitching formats for novelty rather than need · smaller libraries/communities (less battle-testing and tooling) · assuming an alternative is automatically “secure” — implementation still matters · interop friction, since the wider world overwhelmingly speaks JWT.
