JWKS & key rotation

With asymmetric signing, every verifier needs the issuer's public key — and that key shouldn't live forever. This chapter covers how keys are published as a JWKS, how a token points to the right one with kid, and how to rotate keys without invalidating tokens that are still in flight.

What is a JWKS?

A JSON Web Key Set is simply a JSON document with a keys array, where each entry is a public key in JWK form. Issuers publish it; verifiers fetch and cache it, then pick whichever key matches the token they're checking.

{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "kid": "2024-05-key-a",
      "alg": "RS256",
      "n": "0vx7agoebGcQSuuPiLJXZ...",
      "e": "AQAB"
    },
    {
      "kty": "EC",
      "use": "sig",
      "kid": "2024-05-key-b",
      "crv": "P-256",
      "x": "f83OJ3D2xF1Bg8vub9tLe...",
      "y": "x_FEzRu9m36HLN_tue659..."
    }
  ]
}

Note these are public keys only — safe to expose. Each carries a kid (key ID) so a token can name exactly which one signed it, and a use (sig for signing) so the right key is chosen for the right job.

The kid link

The token's header carries a matching kid:

{ "alg": "RS256", "typ": "JWT", "kid": "2024-05-key-a" }

The verifier reads kid, looks up that key in the JWKS, and verifies with it. This indirection is what makes rotation possible: multiple keys can coexist, each addressable by ID.

Treat kid as an opaque lookup keyMatch it against your known key set only. Never use it to build a file path or SQL query, and never fetch a key from a URL the token supplies — those are the kid / jku injection attacks.

Discovery endpoints

So verifiers don't hard-code keys, issuers expose the JWKS at a stable URL — conventionally /.well-known/jwks.json. In OpenID Connect, the discovery document at /.well-known/openid-configuration advertises that location via its jwks_uri field. A verifier fetches the discovery doc once, learns the jwks_uri, then pulls keys from there.

GET /.well-known/openid-configuration HTTP/1.1
Host: auth.example.com

→ { "issuer": "https://auth.example.com",
    "jwks_uri": "https://auth.example.com/.well-known/jwks.json",
    ... }

Rotating without downtime

Keys should rotate periodically — to limit the damage if one ever leaks, and as basic hygiene. The trick is doing it without rejecting tokens that were signed with the old key and haven't expired yet. The answer is an overlap window:

1

Publish the new key

Add the new public key (with a fresh kid) to the JWKS alongside the current one. Don't sign with it yet.

2

Let verifiers pick it up

Wait for caches to refresh so verifiers know about both keys.

3

Switch signing

Start signing new tokens with the new key. Tokens now arrive under both kids — and both verify.

4

Drain, then retire

Keep the old key in the JWKS until every token it signed has expired, then remove it.

Don't remove the old key too earlyIf you pull it before its tokens expire, valid sessions break. The overlap must be at least as long as your access-token lifetime.

Caching & unknown keys

Verifiers should cache the JWKS, not fetch it on every request — otherwise your auth server becomes a bottleneck (and a denial-of-service target). The standard pattern: cache keys, and if a token arrives with an unknown kid, refresh the set once (rate-limited) to pick up a freshly rotated key, then verify. Good libraries do this for you.

import * as jose from 'jose';

// Fetches, caches, and refreshes the key set automatically;
// selects the key matching the token's "kid"
const JWKS = jose.createRemoteJWKSet(
  new URL('https://auth.example.com/.well-known/jwks.json')
);

const { payload } = await jose.jwtVerify(token, JWKS, {
  algorithms: ['RS256'],
  issuer:   'https://auth.example.com',
  audience: 'https://api.example.com',
});

Pitfalls

Watch out forFetching the JWKS per request (latency + DoS) · trusting a token-supplied key URL (jku) instead of your configured endpoint · removing a retired key before its tokens expire · omitting kid so you can't rotate cleanly · forgetting to still pin algorithms when verifying against a JWKS.
