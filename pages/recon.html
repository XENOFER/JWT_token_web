Bug Hunting · Recon

Recon & attack-surface mapping

Most real-world bugs aren't found by clever exploitation — they're found by seeing something nobody else bothered to look at. Reconnaissance is the unglamorous, decisive first phase: building a complete map of what a target exposes, so you know where to point everything that follows.

Stay in scopeOnly enumerate and test assets that are in scope for a bug bounty program, covered by a signed engagement, or that you own. Recon can touch a lot of infrastructure quickly — out-of-scope probing is how researchers get banned or worse.

Start with scope

Before a single tool runs, read the rules. A bug bounty program's scope tells you which domains, apps, and asset types are fair game — and which are explicitly off-limits. A red-team engagement has rules of engagement and an objective. Recon that ignores scope isn't thorough, it's reckless. Write the in-scope and out-of-scope lists down and keep them in front of you.

Enumerate the assets

For a wildcard scope, the first job is finding everything the organisation runs. Pull subdomains from passive sources and certificate-transparency logs, then resolve them and probe which are actually alive:

# Passive subdomain discovery → probe which hosts are live
subfinder -d target.com -silent | httpx -silent -title -tech-detect

# Certificate transparency is a goldmine for hidden hostnames
# (e.g. crt.sh) — combine multiple sources, then dedupe

Tools worth knowing: subfinder, amass, and assetfinder for discovery; dnsx to resolve; httpx to probe and grab titles, status codes, and tech. The output is your universe of hosts.

Content discovery

Per host, the visible site is rarely the whole site. Brute-force directories and files, mine JavaScript for endpoints and secrets, and pull historical URLs that may point to forgotten functionality:

# Directory / file discovery
ffuf -w wordlist.txt -u https://target.com/FUZZ -mc 200,301,302,401,403

# Historical URLs from archives often reveal old endpoints/params
gau target.com | sort -u

Use ffuf, gobuster, or dirsearch with good wordlists (SecLists); gau/waybackurls for archived URLs; and read linked JS files for hidden API paths, parameters, and occasionally hard-coded keys. Tools like Arjun help discover hidden parameters.

Fingerprint the stack

Knowing what something runs narrows the bug classes worth chasing. Identify the server, framework, CMS, WAF, and — crucially for this site — the auth provider. Response headers, error pages, cookie names, and tools like Wappalyzer or httpx -tech-detect all leak this. A Django app, a WordPress install, and a bespoke Node API each fail in different ways.

Map the auth & token surface

This is where token bugs begin — and the bridge from general recon to everything else on this site. Catalogue every place authentication happens: login, registration, password reset, refresh, and SSO endpoints; whether sessions ride in cookies or Authorization: Bearer headers; and any identity-provider discovery documents:

# OIDC / OAuth discovery — often wide open and very informative
curl -s https://target.com/.well-known/openid-configuration
# note: authorization_endpoint, token_endpoint, jwks_uri

# The key set itself (public keys the app verifies with)
curl -s https://target.com/.well-known/jwks.json

Once you've found tokens, the JWT testing checklist tells you exactly what to do with them, and Attacking JWTs covers the techniques.

Find the APIs

APIs are a deep, frequently under-tested surface. Hunt for REST and GraphQL endpoints, exposed Swagger/OpenAPI documentation, versioned routes (/v1/, /v2/), and undocumented endpoints referenced only in client JavaScript or mobile traffic. For GraphQL, introspection (where enabled) hands you the entire schema; tools like graphw00f and InQL help.

Automate & monitor

Run template-based scanners to sweep for known issues across many hosts, and — for bounty work — monitor continuously, since new subdomains and freshly shipped features are where the easy, un-dupe'd bugs live:

# Sweep live hosts for known misconfigurations/CVEs with templates
nuclei -l live-hosts.txt

nuclei is the workhorse here. Pair it with scheduled re-runs of your enumeration so you catch changes as they ship.

Organize what you find

Recon produces a flood of data; the hunters who win are the ones who keep it organised. Maintain a living map of hosts, endpoints, parameters, and tech per target — Burp's sitemap plus your own notes — so that when you learn a new technique, you already know exactly where to apply it.
