Sessions vs JWT

JWTs are popular, which is exactly why they're often the wrong default. They're a genuine improvement for some problems and a needless liability for others. This chapter is the honest comparison — including the cases where a plain old session is simply the better engineering choice.

Two models, quickly

A session keeps state on the server: you log in, the server stores a record and gives your browser a random ID in a cookie, and every request is validated by looking that ID up. A JWT keeps state in the token: the server signs your claims and hands them over, then later trusts them by checking the signature — no lookup. (For the full mechanics, see What is a JWT?)

That single difference — where the state lives — cascades into every trade-off below.

The revocation problem

This is the trade-off people underestimate, so it gets its own section. With sessions, logging someone out — or banning them instantly — is a single delete. With JWTs, a signed token stays valid until its exp no matter what; there's nothing to delete. You can approximate revocation (short lifetimes, a jti denylist), but you can't get true instant revocation for free.

If instant revocation is a hard requirement…then pure stateless JWTs are fighting you. Use sessions, or a hybrid (below). “Ban this user right now” should not require waiting fifteen minutes for a token to expire.

When sessions are the better choice

  • Server-rendered, first-party web apps — a cookie and a session store are simpler and battle-tested.
  • A single backend or a monolith — there's no fleet of services that needs to verify tokens independently.
  • Instant logout / ban is required — banking, admin panels, anything with strict access control.
  • You value simplicity — fewer moving parts (no key management, refresh dance, or claim-validation bugs).

When JWTs shine

  • Stateless APIs consumed by many clients, where you don't want a lookup per request.
  • Microservices that each need to verify identity without a shared session store.
  • Third-party verification & SSO — hand out a public key and anyone can verify (see OAuth vs JWT).
  • Serverless / edge, where there's no persistent session infrastructure.

The hybrid middle ground

You don't have to choose purely. The most common production pattern blends both: short-lived JWT access tokens (stateless, fast, verified anywhere) paired with server-stored refresh tokens (revocable, long-lived). You get stateless verification on the hot path and real revocation control where it counts. Variations include “stateful JWTs” checked against a denylist, or opaque reference tokens validated by introspection (see JWT Alternatives).

Best of bothStateless access token (minutes) + revocable refresh token (server-side). This is what the Auth Flow chapter describes — and it's the right default for most token-based APIs.

A quick decision check

1

Is it a single, first-party, server-rendered app?

Lean sessions. You won't miss the complexity.

2

Do multiple services or third parties need to verify identity?

Lean JWT (asymmetric), so verification doesn't need a shared store.

3

Do you need to revoke access instantly?

Use sessions or the hybrid model — not pure stateless JWTs.

4

Still unsure?

Default to sessions for browser-only apps and the hybrid for APIs. Reach for pure JWT only when statelessness is a real, measured need.

Myths worth ignoring

Neither is inherently more secure. Sessions have a smaller attack surface and instant revocation; JWTs add signing and key-management concerns. Security comes from correct implementation, not the choice itself.

Access-token verification is stateless, but refresh tokens, rotation, and revocation lists usually need storage anyway. The “no database” promise rarely survives real requirements.

A shared store like Redis handles enormous session volumes with sub-millisecond lookups. “Sessions don't scale” is usually premature optimisation, not a real constraint.
