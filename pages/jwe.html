JWE — encrypted tokens

Everything so far has been about signed tokens (JWS), where the payload is readable by anyone. Sometimes you need the opposite: a token whose contents are secret. That's JSON Web Encryption — JWE — the encrypted sibling of the JWT family.

JWS vs. JWE

The tokens you've decoded until now are JWS (JSON Web Signature). A signature proves a token wasn't altered and who issued it — but the payload is only Base64URL-encoded, so anyone holding the token can read it. JWE encrypts the payload instead, so only a holder of the right key can read it at all.

JWS — signed

Integrity + authenticity. Payload is readable. Three parts. This is the default “JWT” most systems use.

JWE — encrypted

Confidentiality (and integrity). Payload is unreadable without the key. Five parts.

Three transformations, don't mix them upEncoding (Base64URL) is reversible by anyone. Signing (JWS) proves integrity but reveals content. Encrypting (JWE) hides content. They solve different problems.

Five parts, not three

Where a JWS joins three segments with dots, a compact JWE joins five:

header.encrypted key.iv.ciphertext.tag
Header (alg + enc) Encrypted key Initialization vector Ciphertext Auth tag

Briefly: the header names the algorithms; the encrypted key is the per-message content key wrapped for the recipient; the IV seeds the cipher; the ciphertext is your encrypted payload; and the authentication tag lets the recipient detect tampering. Decryption needs the recipient's key — there's nothing readable to decode by hand.

Two layers of algorithms

JWE uses two algorithm choices working together. The header's alg covers key management (how the content-encryption key is delivered), and enc covers content encryption (the actual symmetric cipher over your payload).

FieldJobCommon values
algKey management — wrap/derive the content keyRSA-OAEP-256, ECDH-ES, A256KW, dir
encContent encryption — encrypt the payloadA256GCM, A128GCM, A256CBC-HS512

dir means a pre-shared symmetric key is used directly (no wrapped key segment); ECDH-ES derives a key via an ephemeral elliptic-curve exchange. The AEAD ciphers (the GCM family) provide both confidentiality and integrity in one step.

When you actually need it

Most systems don't need JWE — and reaching for it is often a sign that something sensitive shouldn't be in the token at all. Prefer keeping secrets server-side and carrying only non-sensitive claims (see Structure). Genuine JWE use cases include:

  • A token must travel through an untrusted intermediary yet carry confidential claims.
  • You're in an ecosystem (some OIDC / FAPI profiles) that mandates encrypted tokens.
  • You need both secrecy and proof of origin — handled with a nested JWT.

Nested JWT = sign, then encryptFor confidentiality and authenticity, first sign the claims as a JWS, then encrypt that JWS as the payload of a JWE. The recipient decrypts, then verifies the inner signature.

Using JWE in practice

With a modern library the two layers are just parameters. Here's the shape with jose in Node — encrypting, then decrypting and validating claims in one step:

import * as jose from 'jose';

// Encrypt → compact JWE (five parts)
const jwe = await new jose.EncryptJWT({ sub: '1024', role: 'user' })
  .setProtectedHeader({ alg: 'RSA-OAEP-256', enc: 'A256GCM' })
  .setIssuer('https://auth.example.com')
  .setAudience('https://api.example.com')
  .setExpirationTime('15m')
  .encrypt(recipientPublicKey);

// Decrypt + validate claims (claims still matter after decryption!)
const { payload } = await jose.jwtDecrypt(jwe, recipientPrivateKey, {
  issuer:   'https://auth.example.com',
  audience: 'https://api.example.com',
});

Pitfalls

Watch out forAssuming encryption replaces validation — still check exp/aud/iss after decrypting · confusing JWE with signing (it's heavier and adds key-management complexity) · mismatched alg/enc support between parties · putting sensitive data in a plain JWS thinking the signature hides it (it doesn't).
