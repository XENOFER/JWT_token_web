Security & crypto

They can be, with correct handling. Most JWT incidents come from implementation mistakes — not pinning the algorithm, not verifying, weak secrets. See Vulnerabilities.

For a single service, HS256 with a long random secret is fine. For multiple/third-party verifiers, go asymmetric — EdDSA or ES256 for new systems, RS256 for maximum interop. Never none. See Algorithms.

Building with JWTs

Prefer an HttpOnly, Secure, SameSite cookie so JavaScript can't read it (mitigating XSS theft), and pair it with CSRF defenses. localStorage is convenient but exposed to any script on the page. See Vulnerabilities.

Keep access tokens short — roughly 5–15 minutes — and use a longer-lived, rotating refresh token for continuity. See Auth Flow.

The access token is short-lived and sent on every request; the refresh token is long-lived, sent only to the refresh endpoint, and used to get new access tokens. See Auth Flow.

You can't “delete” a signed token before it expires. Discard it client-side, revoke the refresh token server-side (rotation helps), keep access tokens short, and use a jti denylist for instant revocation. See Auth Flow.

Sessions for single, server-rendered apps and where instant revocation matters; JWTs for stateless APIs, microservices, and SSO. Often a hybrid is best. See Sessions vs JWT.

Use a maintained library, pin the algorithm, and validate exp/aud/iss — never just decode. See language examples in Libraries.
