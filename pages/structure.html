Chapter 03

Anatomy of a JWT

Strip away the mystique and a JSON Web Token is almost disappointingly simple: three text segments, each Base64URL-encoded, joined by dots. Learn to read every part — then decode one yourself.

Written out, a token follows one fixed shape:

xxxxx.yyyyy.zzzzz
Header — metadata Payload — claims Signature — integrity

The two dots are structural separators, not part of the data. Split on them and you have three independent pieces you can decode on their own. Let's do exactly that.

Part one — the header

The header is a small JSON object describing how the token was signed. In the overwhelming majority of tokens it contains just two fields:

{
  "alg": "HS256",
  "typ": "JWT"
}

alg names the signing algorithm (for example HS256 or RS256), and typ declares the media type. Headers may carry extra fields such as kid (a key identifier), jku/jwk (where to find the verification key), or cty for nested tokens — and several of those become attack surfaces, as the security chapters explain.

The header is attacker-controlledBecause anyone holding a token can rewrite its header, a verifier must never blindly trust alg. Pin the expected algorithm server-side instead.

Part two — the payload and its claims

The payload carries the claims: statements about an entity (typically the user) and metadata about the token itself. Claims fall into three families.

Registered claims

A small set of standardized, optional claims defined by the specification. Using them keeps tokens interoperable. The most common:

ClaimNamePurpose
issIssuerWho created and signed the token.
subSubjectThe principal the token is about (e.g. a user ID).
audAudienceWho the token is intended for; reject if it isn't you.
expExpirationUnix time after which the token must be refused.
nbfNot BeforeUnix time before which the token is not yet valid.
iatIssued AtWhen the token was minted.
jtiJWT IDA unique identifier — useful for revocation lists.

Public & private claims

Public claims are names you define but register or namespace (often as a URI) to avoid collisions across systems. Private claims are custom names agreed upon privately between the parties using the token — things like role, tenant_id, or email. They work fine, but two unrelated systems could give the same private name different meanings, so namespacing matters as you scale.

{
  "sub": "1024",            // registered
  "iss": "https://auth.example.com",
  "exp": 1735689600,
  "role": "admin",          // private claim
  "https://example.com/tenant": "acme"  // public (namespaced)
}

Base64URL is encoding, not encryption

This is the single most important — and most misunderstood — fact about JWTs. The header and payload are Base64URL-encoded, a reversible transformation that makes binary-safe, URL-safe text. It uses - and _ instead of + and /, and drops = padding.

Anyone can reverse it with one line of code — no key required:

// Decode a JWT payload in the browser — no secret needed
const [header, payload, signature] = token.split('.');

const fromB64Url = (s) =>
  decodeURIComponent(
    atob(s.replace(/-/g, '+').replace(/_/g, '/'))
      .split('')
      .map(c => '%' + c.charCodeAt(0).toString(16).padStart(2, '0'))
      .join('')
  );

console.log(JSON.parse(fromB64Url(payload))); // fully readable

Never put secrets in a payloadPasswords, API keys, or personal data placed in a JWT payload are effectively public. The signature stops tampering, not reading. If you need confidentiality, encrypt the token (JWE) or keep sensitive data server-side.

Part three — the signature

The signature is what turns three readable strings into something trustworthy. It's computed over the encoded header and payload, using the algorithm named in the header and a key:

signature = HMAC_SHA256(
    base64url(header) + "." + base64url(payload),
    secret
)

Change a single byte of the header or payload and the recomputed signature won't match — so the server rejects it. With a symmetric algorithm the same secret signs and verifies; with an asymmetric one a private key signs and a public key verifies. Either way, the signature guarantees integrity and authenticity, but — to repeat the point that trips people up — not confidentiality.

Mental modelHeader = "how I'm signed." Payload = "what I claim." Signature = "proof I haven't been altered by someone without the key."
