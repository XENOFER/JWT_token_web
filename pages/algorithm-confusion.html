Algorithm confusion

Also called key confusion, this is the most elegant JWT attack: you make a server that expects an RS256-signed token happily verify one you signed with HS256 — using the server's own public key as the HMAC secret. Here's exactly how, step by step.

Authorized targets onlyPractise this on PortSwigger's algorithm-confusion labs or systems you're permitted to test — never anywhere else.

Symmetric vs. asymmetric — the crux

Recall from the Algorithms chapter: RS256 signs with a private key and verifies with the matching public key, while HS256 signs and verifies with one shared secret. The public key is exactly that — public. The attack hinges on a single observation: if a verifier lets the token choose the algorithm and reuses the same key material, then switching to HS256 turns the freely-available public key into the “secret” you need to forge a valid signature.

How the vulnerability arises

It appears when verification logic reads alg from the token and branches on it, but ends up feeding the RSA public key into HMAC verification — or hands a single generic verify() the public key for whatever algorithm the token declares:

// VULNERABLE — the algorithm comes from the token, one key reused
const header = decodeHeader(token);
// HS256 path receives the RSA *public* key as the HMAC secret:
jwt.verify(token, rsaPublicKey, { algorithms: [header.alg] });

An attacker who knows rsaPublicKey (they do — it's public) can now compute a valid HS256 signature over any payload.

Performing the attack

Step 1 — Obtain the server's public key

Most asymmetric setups publish it. Check the standard locations: /jwks.json, /.well-known/jwks.json, or the OIDC discovery document at /.well-known/openid-configuration (whose jwks_uri points to the key set). You'll get one or more keys in JWK form.

Step 2 — Convert it to the right format

When the server does HMAC, it uses the key as a string of bytes — so you need the exact PEM / X.509 representation it would use, down to the header lines and newlines. Convert the JWK to PEM with jwt_tool, openssl, or Burp's JWT Editor key tools. Getting these bytes precisely right is the step people most often fumble.

# Burp JWT Editor: Keys → New RSA Key (paste the JWK) → copy the PEM
# or with jwt_tool, which can derive/convert and sign in one step (Step 4)

Step 3 — Modify your JWT

Change the header's alg to HS256 and edit the claims to whatever proves impact — typically a privileged sub or role:

{ "alg": "HS256", "typ": "JWT" }
// payload, e.g.:  { "sub": "administrator" }

Step 4 — Sign with the public key as the secret

Compute the HMAC over header.payload using the PEM public key as the HMAC key. jwt_tool does the whole thing; Burp's JWT Editor can sign with a symmetric key you create from the PEM:

# jwt_tool key-confusion mode, supplying the server's public key as the "secret"
python3 jwt_tool.py <token> -X k -pk public.pem
# → outputs an HS256 token a vulnerable server accepts as genuine

Send the forged token. A server with the flaw verifies it and grants the access the claims assert.

Deriving the public key from tokens

What if the public key isn't exposed anywhere? With two valid tokens signed by the same RSA key, the key can often be recovered mathematically — tooling such as rsa_sign2n (shipped alongside jwt_tool) computes candidate public keys from the signatures. Once you have a candidate, proceed exactly as above.

Prevention

How to shut it downPin a single expected algorithm at verification rather than reading it from the token · never use the same key material under two different algorithm types · prefer library APIs that bind a key to one algorithm so an HS256 token can't be verified with an RSA key.
