Attack demonstrations

Sandbox & ethicsEvery demo below runs against fabricated tokens generated in your browser. They illustrate why each defense exists — for learning and defensive review only. Never test these techniques against systems you don't own or have explicit permission to assess.

Critical

The none algorithm

Some libraries once honoured a header of {"alg":"none"} and skipped signature verification entirely. An attacker can rewrite a token's header to none, strip the signature, and walk in. A correct verifier refuses this outright.

Click the button to run the demonstration.

PreventionPin an explicit allow-list of algorithms server-side and reject none. Never derive the verification algorithm from the token's own header.

High

Weak-secret brute force

HMAC tokens are only as strong as their secret. If the secret is a common word, it can be recovered offline by trying candidates until one reproduces the signature — then the attacker can mint any token.

Click to attempt recovery against the demo wordlist.

PreventionUse a long, random secret of at least 256 bits from a CSPRNG. For multi-service setups, prefer asymmetric keys (RS/ES) so only the issuer holds signing material.

High

Payload tampering

Because the payload is only encoded, an attacker can rewrite a claim — say role from user to admin. Without the secret they can't regenerate the signature, so a verifier that actually checks it will reject the token.

Click to edit the payload and re-check the signature.

PreventionAlways verify the signature before trusting any claim, and ensure verification failures are fatal — never "log and continue."

Common

Expired / long-lived tokens

A signature can be perfectly valid while the token is far too old to trust. Signature validity and token validity are two different checks — both must pass.

Click to compare the two checks.

PreventionKeep access-token lifetimes short, validate exp and nbf with minimal clock skew, and use refresh tokens for longevity.
