Chapter 04

Signing algorithms

A JWT's signature is only meaningful once you know how it was produced. The alg field names that method — and the choice between a shared secret and a key pair shapes everything from who can verify a token to how you defend it. This chapter maps the whole landscape.

Where the algorithm comes from

Every signed JWT declares its algorithm in the header's alg field — for example {"alg":"HS256"}. That value tells a verifier which procedure and key type to expect. The signing itself is defined by a sibling standard, JWS (JSON Web Signature, RFC 7515); JWT just carries the result.

One thing to hold onto from the very start: the header is part of the token, so it is attacker-controlled. A verifier must decide in advance which algorithm(s) it will accept and ignore any attempt by the token to choose for it. We'll return to why in the algorithm-confusion section.

Symmetric vs. asymmetric

Every JWT algorithm (except none) falls into one of two camps, and the difference is the single most important idea on this page.

Symmetric · HMAC (HS*)

The same secret signs and verifies. Simple and fast — but anyone able to verify can also forge.

Asymmetric · RSA / EC / EdDSA

A private key signs; a freely-shareable public key only verifies. Verifiers can check tokens but can't mint them.

That distinction drives the practical decision. With a symmetric algorithm there is one secret, so it suits a single service (or a tightly trusted group) that both issues and checks its own tokens. With an asymmetric algorithm you can hand the public key to any number of services — even third parties — and they can verify tokens without ever being able to issue one. That property is exactly what makes asymmetric signing the backbone of single sign-on and OpenID Connect.

A keyed hash (HMAC) over the token, using SHA-256, -384, or -512. One shared secret both signs and verifies. It's the fastest option and the simplest to set up — there are no keys to generate, just a secret string.

The catch is entirely about that secret: it must be long, random, and high-entropy (think ≥256 bits from a secure generator), and every party that verifies necessarily holds the power to sign. Great for a single backend; risky to hand around.

RSASSA-PKCS#1 v1.5 signatures with SHA-2. Asymmetric: a private key signs, a public key verifies. RS256 is the most universally supported JWT algorithm and the default across much of the OpenID Connect ecosystem.

Trade-offs: keys should be at least 2048-bit (3072+ for longer-term security), signatures are large (256 bytes at 2048-bit), and signing is comparatively slow. The PKCS#1 v1.5 padding is older; where you can, prefer PSS (below).

The same RSA keys, but with the modern, randomized PSS padding scheme rather than PKCS#1 v1.5. It has stronger security proofs and is the recommended choice when you're committed to RSA. Support is good but not quite as universal as RS256, so confirm both ends agree.

Elliptic-curve signatures over NIST curves: ES256 uses P-256, ES384 uses P-384, and ES512 uses P-521 (yes — 521, not a typo). Asymmetric, with much smaller keys and signatures than RSA at equivalent strength, and fast all round. ES256 is extremely common in modern OIDC deployments.

ECDSA's one historical footgun is that each signature needs a unique, unpredictable random value; reusing it leaks the private key. Reputable libraries handle this for you (often via deterministic nonces), so it's not something you implement by hand — but it's why EdDSA, which removes the hazard by design, is appealing.

Edwards-curve signatures (the alg value is literally EdDSA). Deterministic, fast, with tiny keys and signatures, and designed to be hard to misuse — no per-signature randomness to get wrong. For brand-new systems it's often the best default. The only caveat is reach: some older libraries and platforms don't support it yet, so check compatibility before committing.

A token with {"alg":"none"} and an empty signature. It exists in the spec for cases where integrity is guaranteed by other means, but in practice it's a notorious vulnerability: any library that honours it will accept a completely forged token. Treat none as something to reject outright — never as a valid choice. See it broken in the attack demos.

Which should you use?

Two questions get you most of the way:

1

Does anything other than the issuer need to verify tokens?

If yes — separate services, third parties, public clients — go asymmetric so the verification key can be shared without granting the ability to forge. If the same service both issues and verifies, symmetric (HS256 with a strong random secret) is perfectly fine and simpler.

2

If asymmetric, how much do you value modern crypto vs. maximum compatibility?

For new systems, prefer EdDSA (Ed25519) or ES256 — small, fast, robust. If you must interoperate with everything (or a provider mandates it), RS256 is the safe, universal choice; use PS256 instead where both ends support it.

Rules of thumbNew & you control both ends → EdDSA or ES256. Need broad interop / OIDC → RS256 (or PS256). One internal service → HS256 with a 256-bit random secret. And always — never none.

A word on algorithm confusion

Because the token names its own algorithm, a verifier that blindly trusts alg can be tricked. The classic case: a server expects RS256 and verifies with an RSA public key. An attacker changes the header to HS256 and signs the token using that public key — which is, by definition, public — as if it were an HMAC secret. A naive library that reads alg from the header, then feeds the configured RSA public key into HMAC verification, will happily accept the forgery.

The fix is simple and non-negotiable: pin the accepted algorithm(s) server-side, and never let one key be used under two different algorithm types.

// SAFE — the server dictates the algorithm; the token cannot
const claims = jwt.verify(token, PUBLIC_KEY, {
  algorithms: ['RS256']   // pinned; an "alg":"HS256" token is rejected outright
});

Never derive the algorithm from the tokenTreat header.alg as a hint to reject mismatches, not as an instruction to follow. Full coverage of this and related header attacks is in the Vulnerabilities chapter.
