Chapter 02

What is a JSON Web Token?

Before you can secure JWTs, it helps to know what one actually is and why it exists. In short: a JWT is a small, signed packet of JSON that lets a server trust a claim — like “this user is an admin” — without looking anything up. This chapter explains that idea from the ground up.

A token, defined

A JSON Web Token — JWT, usually pronounced “jot” — is an open standard (RFC 7519) for transmitting information between two parties as a compact, URL-safe, digitally signed JSON object. That signature is the whole point: because the data is signed with a key, whoever receives the token can confirm two things — that the contents haven't been tampered with, and (with the right kind of key) who issued it.

“Compact” matters too. A JWT is just text, small enough to drop into an HTTP header or a URL, so it travels easily on every request. And it's self-contained: everything the server needs to make a trust decision is carried inside the token, not stored somewhere else.

In one sentenceA JWT is a signed JSON statement a server hands to a client, and later trusts on sight — because the signature proves it wasn't forged or altered.

The problem it solves: stateless authentication

To see why JWTs caught on, picture the older approach — server-side sessions. When you log in, the server creates a session record (in memory, Redis, or a database) and sends your browser a random session ID in a cookie. On every following request, the server takes that ID, looks up the matching record, and only then knows who you are.

That works beautifully on a single server. It gets awkward at scale: if you run ten servers behind a load balancer, they all need to reach the same session store, or you have to pin each user to one machine. Every single request costs a lookup, and the server is forced to remember something about everyone currently logged in.

JWTs flip the model. Instead of the server remembering who you are, it signs a statement of who you are and hands it to you. On later requests you present that signed statement, and any server holding the verification key can check the signature and trust it — no shared store, no lookup. The state moved out of the server and into the token. That's what “stateless” means here.

Sessions vs. tokens at a glance

Neither approach is universally “better” — they make different trade-offs. The big one is where trust lives and what you give up for it.

The life of a token

From the moment you log in to the moment the token expires, a JWT follows the same arc. Here it is as a request-by-request exchange between a browser and a server:

Spelled out as steps, the same lifecycle is:

1

Authenticate

The user proves who they are — typically a username and password, or a third-party login.

2

Issue & sign

The server builds a token with claims like sub, role, and exp, then signs it with its key.

3

Store

The client keeps the token — ideally in an HttpOnly cookie, or in memory. (The Best Practices chapter covers the trade-offs.)

4

Send on each request

The token rides along in the Authorization: Bearer <token> header (or the cookie).

5

Verify

The server checks the signature and the claims (is it expired? is it for me?). If everything holds, the request is trusted — no lookup needed.

6

Expire & refresh

Short-lived access tokens expire quickly; a longer-lived refresh token is exchanged for a fresh one when needed.

What it looks like in practice

On the wire, sending a token is nothing more than an HTTP header:

GET /api/profile HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMDI0In0.…

And verifying it on the server is a single call — notice there's no session store in sight, and that the expected algorithm is pinned explicitly (a habit the Security chapters will explain):

import jwt from 'jsonwebtoken';

// Runs on every protected request — stateless, no DB read
function authenticate(req) {
  const header = req.headers.authorization || '';
  const token = header.split(' ')[1];          // "Bearer <jwt>"

  try {
    const claims = jwt.verify(token, PUBLIC_KEY, { algorithms: ['RS256'] });
    return claims;        // trusted: { sub, role, exp, ... }
  } catch (err) {
    throw new Error('Invalid or expired token');
  }
}

Where JWTs shine — and where they don't

JWTs are a tool, not a default. They're a great fit for some jobs and a poor one for others.

Great for
  • Stateless REST / GraphQL APIs
  • Microservices passing identity between each other
  • Single sign-on and OpenID Connect
  • Short-lived access tokens
  • Serverless, where there's no session store
Be careful with
  • Anything needing instant logout or ban
  • Storing sensitive or large data (the payload is readable)
  • Treating one long-lived token as a whole session
  • Rolling your own signing or validation logic

The revocation catchA signed token stays valid until it expires — you can't “delete” it the way you delete a session. Plan around this: keep access tokens short-lived, use refresh tokens, and for true revocation keep a denylist keyed by the jti claim.

A quick analogy

Think of a festival wristband. At the gate, staff check your ticket once — that's logging in. In return you get a tamper-evident wristband: that's your signed token. Inside the festival, nobody walks you back to the box office; staff just glance at the wristband and let you through, which is the server verifying the signature instead of hitting the database. Anyone can see what tier your band is (the payload is readable), but the hologram means they can't forge one. And it only works until the festival ends — the token's exp.

TakeawayA JWT trades a database lookup for a signature check. That's a great deal for scale and simplicity — as long as you respect what the signature does (proves integrity) and doesn't do (provide secrecy or easy revocation).
