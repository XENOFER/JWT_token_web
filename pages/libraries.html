Chapter 11

Libraries & framework examples

You should almost never implement JWT signing or verification by hand — that's how the vulnerabilities in the previous chapter creep in. Reach for a maintained library, then use it correctly. Here's how, in six ecosystems, with the same defensive shape every time.

Rules that apply everywhere

Languages differ; the secure recipe doesn't. Whatever stack you're on, a correct verification does all of this:

The universal checklistUse a maintained library · verify, never just decode · pin the algorithm(s) explicitly · validate exp/nbf, aud and iss · load keys from a trusted source (never the token's own headers) · keep secrets/keys in a vault, not in code · treat any failure as a hard reject.

Don't roll your ownHand-built base64 splitting and HMAC comparisons are exactly where alg:none, algorithm confusion, and timing bugs slip in. A vetted library closes those by default — see the Vulnerabilities chapter for what you'd otherwise have to get right.

Secure verification, by language

Each example pins the algorithm and validates the standard claims. (APIs shift between versions — treat these as the shape to aim for and check your library's current docs.)

jsonwebtoken  npm i jsonwebtoken

import jwt from 'jsonwebtoken';

const claims = jwt.verify(token, PUBLIC_KEY, {
  algorithms: ['RS256'],                 // pin — rejects none & alg confusion
  issuer:   'https://auth.example.com',  // checks iss
  audience: 'https://api.example.com',   // checks aud
});
// exp / nbf enforced automatically; throws on any failure

Avoidjwt.decode(token) to read identity — it does not verify. Always pass algorithms.

PyJWT  pip install pyjwt[crypto]

import jwt  # PyJWT — note: decode() DOES verify here

claims = jwt.decode(
    token,
    PUBLIC_KEY,
    algorithms=["RS256"],                  # pin
    issuer="https://auth.example.com",
    audience="https://api.example.com",
    options={"require": ["exp", "iat"]},
)

Avoidoptions={"verify_signature": False} and omitting algorithms — both disable real protection.

firebase/php-jwt  composer require firebase/php-jwt

use Firebase\JWT\JWT;
use Firebase\JWT\Key;

// Algorithm is pinned by the Key — the token's header can't override it
$claims = JWT::decode($jwt, new Key($publicKeyPem, 'RS256'));

if (($claims->iss ?? null) !== 'https://auth.example.com') {
    throw new Exception('bad issuer');
}

AvoidTrusting $claims->iss/aud without checking them, and accepting an algorithm derived from the token.

Auth0 java-jwt  com.auth0:java-jwt

Algorithm algorithm = Algorithm.RSA256(publicKey, null);

JWTVerifier verifier = JWT.require(algorithm)   // pins RS256
    .withIssuer("https://auth.example.com")
    .withAudience("https://api.example.com")
    .build();

DecodedJWT jwt = verifier.verify(token);        // throws on failure

AvoidJWT.decode(token) (no verification) and skipping withIssuer/withAudience.

golang-jwt/jwt v5  go get github.com/golang-jwt/jwt/v5

token, err := jwt.Parse(raw, func(t *jwt.Token) (any, error) {
    if _, ok := t.Method.(*jwt.SigningMethodRSA); !ok {   // pin the family
        return nil, fmt.Errorf("unexpected alg: %v", t.Header["alg"])
    }
    return publicKey, nil
},
    jwt.WithValidMethods([]string{"RS256"}),
    jwt.WithIssuer("https://auth.example.com"),
    jwt.WithAudience("https://api.example.com"),
)

AvoidReturning the key without checking t.Method — the classic Go algorithm-confusion bug.

Microsoft.IdentityModel.Tokens

var handler = new JsonWebTokenHandler();

var result = handler.ValidateToken(token, new TokenValidationParameters {
    ValidateIssuerSigningKey = true,
    IssuerSigningKey         = signingKey,
    ValidAlgorithms          = new[] { "RS256" },   // pin
    ValidIssuer              = "https://auth.example.com",
    ValidAudience            = "https://api.example.com",
    ValidateLifetime         = true,
});
if (!result.IsValid) throw result.Exception;

AvoidSetting ValidateIssuer/ValidateAudience/ValidateLifetime to false, or leaving ValidAlgorithms unset.

The mistakes every language shares

Reading claims from a decode call trusts attacker-controlled data. Always verify the signature first, and only then read claims.

Letting the token's header choose the algorithm enables none and RS→HS confusion. Pass an explicit allow-list every time.

A valid signature isn't enough. Verify exp/nbf, and check aud and iss so tokens can't be reused across services.

Secrets in source or short HS* keys are brute-forceable and leak via repos. Use long random keys from a secrets manager, and rotate them.

A broad try/catch that logs and proceeds turns a rejection into an acceptance. Make verification failure stop the request.
