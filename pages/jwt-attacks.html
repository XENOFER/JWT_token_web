Attacking JWTs

The defensive catalogue tells you what can go wrong; this is the other side of the glass — how those flaws are actually exploited. It's the methodology and tooling behind the PortSwigger Web Security Academy JWT labs and real authorized assessments: how to spot each weakness, how to exploit it, and what to reach for.

Authorized targets onlyThese techniques are for deliberately vulnerable labs — like PortSwigger's free Web Security Academy — and systems you have explicit written permission to test. Using them against anything else is illegal. Learn to attack so you can defend.

What are JWT attacks?

A JWT attack manipulates a token — its header, its claims, or its signature — to make a server trust something it shouldn't: a forged identity, an elevated role, or a token it ought to reject. Because a JWT frequently is the session, nearly all of these attacks aim at one of two targets: how the server verifies the signature, or how blindly it trusts the token's contents.

Impact

When it works, the payoff is usually authentication bypass and privilege escalation — logging in as another user, flipping a role or admin claim, or taking over an account outright. Where tokens carry data, the same flaws can leak it. In a lab you'll typically prove impact by reaching an admin-only function; in the real world the consequences scale with what the token protects.

How the vulnerabilities arise

They come from how tokens are handled, not from the format. The usual roots: signatures that aren't verified (or are only checked when present), servers that trust the algorithm or key a token names for itself, weak or guessable HMAC secrets, and missing claim checks (exp, aud, iss). Very often it's a perfectly good library used incorrectly — verification disabled, or algorithms left unpinned.

A testing workflow

1

Capture & decode

Grab the token (Burp, jwt_tool, or the Playground). Note the alg, the interesting claims (role, admin, sub), and whether exp/aud are present.

2

Probe signature handling

Does the server accept a tampered payload? A stripped signature? alg:none? This is the highest-value check.

3

If HMAC, attack the secret

Try to crack a weak HS* secret offline.

4

Inspect header parameters

Look at kid, jku, jwk, x5u — anything that selects a key — for injection.

5

If RSA, test algorithm confusion

Try turning an RS256 verifier into an HS256 one (its own walkthrough).

6

Forge & replay

Rebuild the token with the claim you want and send it.

Tooling

Three tools cover almost everything:

  • Burp Suite + JWT Editor — a free BApp-store extension that adds a JSON Web Token view to decode and edit the header/payload, re-sign, and run helpers (embedded jwk, alg:none, signing with a weak key). The go-to for the PortSwigger labs.
  • jwt_tool — a command-line Swiss-army knife for inspecting, tampering, cracking, and exploiting tokens.
  • hashcat — fast offline cracking of HMAC secrets.
# Decode & inspect a token
python3 jwt_tool.py <token>

# Tamper with claims interactively
python3 jwt_tool.py <token> -T

# Crack a weak HMAC secret with a wordlist
python3 jwt_tool.py <token> -C -d jwt.secrets.list

# Exploit: alg:none variants
python3 jwt_tool.py <token> -X a

# Exploit: algorithm / key confusion (RS256 → HS256)
python3 jwt_tool.py <token> -X k -pk public.pem

# Inject a self-signed key via the jwk header
python3 jwt_tool.py <token> -X i
# run with -h for the current, full flag list
# Mode 16500 = JWT (HMAC). Put the whole token on one line in jwt.txt
hashcat -m 16500 -a 0 jwt.txt wordlist.txt
# Popular wordlists for this: jwt.secrets.list, rockyou.txt

Exploiting flawed signature verification

Accepting arbitrary signatures

Some servers only verify a signature when one is present, or carry a logic bug that never truly checks it. Test it: edit a claim — say role to admin — and send the token with its original (now mismatched) or a garbage signature. If the request succeeds, the server isn't verifying. In Burp's JWT Editor, just change the payload and send without re-signing.

Accepting tokens with no signature (alg:none)

The unsigned variant. Set the header's alg to none, change whatever claims you like, and drop the signature — but keep the trailing dot, so the token ends in .. Many naive filters block the literal "none" but miss case variations, so also try None, NONE, and nOnE. If it's accepted, you can forge anything.

{ "alg": "none", "typ": "JWT" }
// token becomes:  base64url(header).base64url(payload).   ← empty third part

Brute-forcing weak secrets

If the token uses HS256/384/512, the signature is only as strong as the secret. Save the token and run hashcat (mode 16500) or jwt_tool against a wordlist — the well-known jwt.secrets.list and rockyou.txt recover a surprising number. Once you have the secret, forge a token with elevated claims and sign it with that secret; it will verify cleanly. (PortSwigger's weak-signing-key lab is exactly this.)

JWT header-parameter injection

The header can carry parameters telling the verifier which key to trust. If the server believes them, you get to supply the key.

Injecting via the jwk parameter

The jwk header can embed a public key inline. Generate your own key pair, place your public key in jwk, edit the claims, and sign with your matching private key. A server that verifies against the embedded key accepts the forgery. Burp's JWT Editor automates this as Attack → Embedded JWK.

Injecting via the jku parameter

jku is a URL pointing to a JWKS. Host your own key set somewhere the server will fetch, point jku at it, and sign with your key. You may need to defeat an allow-list — sometimes via SSRF, an open redirect, or a URL the server already trusts.

Injecting via the kid parameter

kid selects a key by identifier. If it's used to build a file path, point it at a predictable file — the classic is ../../../../../dev/null — so the "key" is empty, then sign with an empty key. If it's used in a SQL query, inject to return a value you control and use that as the key.

Other interesting parameters

x5c and x5u are the certificate equivalents of jwk and jku and carry the same risks; cty (content type) and nested tokens can open further avenues. Treat every header parameter the server acts on as attacker-controlled.

Algorithm confusion

The marquee attack — coercing a server that expects RS256 into verifying a token you signed with HS256, using its own public key as the HMAC secret — is involved enough to get its own page.

Preventing these attacks

Defender's checklistPin the accepted algorithm(s) and reject none (including case variants) · use a long, random HMAC secret · never trust jwk/jku/kid/x5c/x5u from the token — use server-configured keys only · validate exp, aud and iss · keep tokens short-lived.
