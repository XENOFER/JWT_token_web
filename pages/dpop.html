DPoP & sender-constrained tokens

A bearer token has one fatal property: whoever holds it can use it. Steal one and you're in. Sender-constraining fixes that by binding a token to a key only the legitimate client controls — so a stolen token, on its own, is worthless. Two mechanisms do this: DPoP and mTLS.

The bearer problem

Throughout the auth flow, the access token is a bearer credential: the server checks the token is valid and grants access, with no proof that the sender is the party it was issued to. That's why a token leaked via XSS, a proxy log, or a misrouted request can be replayed by an attacker for as long as it's valid (see token replay). Sender-constraining adds exactly that missing proof.

DPoP — proof of possession

DPoP (Demonstrating Proof-of-Possession, RFC 9449) is an application-layer scheme. The client generates its own key pair and proves, on every request, that it holds the private key. The access token is bound to that key, so it only works when accompanied by a matching proof.

The binding lives in a confirmation claim, cnf, carrying the JWK thumbprint (jkt) of the client's public key:

{
  "sub": "1024",
  "aud": "https://api.example.com",
  "exp": 1735689600,
  "cnf": { "jkt": "0ZcOCORZNYy-DWpqq30jZyJGHTN0d2HglBV3uiguA4I" }
}

On each call, the client sends a small signed JWT — the DPoP proof — in a DPoP header. It's signed by the client's private key and ties the request to a specific method and URL:

// header
{ "typ": "dpop+jwt", "alg": "ES256", "jwk": { /* client public key */ } }
// payload
{
  "htm": "GET",                       // HTTP method
  "htu": "https://api.example.com/orders",  // HTTP URI
  "iat": 1735689000,
  "jti": "f9a1...unique-per-proof"
}

How a DPoP request checks out

1

Client holds a key pair

Generated locally; the private key never leaves the client.

2

Token is bound

At issuance, the access token gets a cnf.jkt equal to the thumbprint of the client's public key.

3

Each request carries a fresh proof

The client signs a DPoP proof JWT for that exact method + URL and attaches it.

4

Server verifies the pair

It checks the proof's signature, that htm/htu match the request, and that the proof key's thumbprint equals the token's cnf.jkt. A stolen token without the private key fails here.

mTLS-bound tokens

The other approach binds the token at the transport layer. With mutual TLS (RFC 8705), the client authenticates its TLS connection with a certificate, and the access token records that certificate's thumbprint — again under cnf, this time as x5t#S256. The resource server only honours the token over a TLS connection presenting the same certificate.

When to use it

Sender-constraining adds real complexity, so reserve it for where token theft is both likely and costly: public clients exposed to XSS (single-page and mobile apps), high-value or financial-grade APIs (FAPI profiles), and any system where a replayed token would be a serious incident. For a typical first-party app with short-lived tokens and good XSS hygiene, plain bearer tokens are usually acceptable.

Pitfalls

Watch out forDPoP proof replay — bind proofs to method/URL, enforce a short iat window, and track jti (often with a server nonce) so a captured proof can't be reused · clock skew on the proof's freshness check · treating DPoP as a TLS replacement (you still need TLS) · the added key-management burden on clients.
